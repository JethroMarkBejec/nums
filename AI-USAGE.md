# AI Usage in Flutter/Dart Code

During the initial NUMS implementation from September 20 to October 4, 2026, I used Claude and OpenAI Codex. My retrospective estimate is that AI helped with about 80% of that initial implementation. I contributed about 20%, including writing the initial welcome, login, and sign-up screens, directly writing or editing screen UI across nearly all other screens, and making the app's visual design and layout decisions. The main exception is Chip's assistant/animation screen, which was AI-assisted. This is an estimate, not a line-by-line measurement. I continued revising the app after October 4, including hands-on changes I made myself and AI-assisted changes. I also used OpenAI Codex for Flutter/Dart compatibility and analyzer cleanup on October 11. Those later changes are described separately and are not included in the original 80/20 estimate.

I did not keep a dated prompt log or separate commits for each screen. These entries describe the Flutter/Dart work from memory; the linked commits contain grouped changes. The dates below distinguish my recorded initial-use window from later code commit dates; a commit date shows when code landed, not necessarily the exact day I prompted an assistant. The project commits are under my GitHub account, but that does not mean every line in a commit was hand-written by me or generated by AI. I have not assigned an exact assistant to an individual change where I did not record it.

## 2. Where the AI got it wrong

These are three problems I observed while reviewing AI-assisted Flutter code. A linked commit date shows when the related code landed, not necessarily when the incorrect suggestion was generated. Where the original assistant or prompt date was not recorded, I say so rather than guessing.

### Checkout could show payment as pending

- **What the first checkout implementation did:** Its confirmation dialog said, “Place this order? Payment will show as pending until a payment provider is connected,” and it created the order before any payment step. That was the implementation I reviewed and asked to change; the grouped commit does not show which person or assistant wrote that exact line.
- **Date / tools:** The initial pending-payment flow landed October 4; the pay-before-confirmation correction landed October 5 with OpenAI Codex. I did not record which assistant first proposed the pending flow or the exact date I noticed the mismatch.
- **What was wrong:** It confirmed an order without first completing payment, contrary to the flow I wanted, even though the rest of the app presented checkout as a payment step.
- **What I did instead:** I specified that a local payment simulation must succeed before the order is confirmed, reviewed the payment warning and result, and kept an exception for allergy orders that need staff approval before payment. The implemented correction only marks a normal order as paid after the repository reports success.
- **Flutter/Dart files:** `lib/screens/customer/ordering/payment_screen.dart`, `lib/screens/customer/ordering/confirmation_screen.dart`, `lib/providers/order_provider.dart`.

- **`lib/screens/auth/login_screen.dart`:** I put email and password in a `Form` with a `GlobalKey<FormState>` and text controllers, then connected the submit action to the local `AuthProvider.signIn` flow. Validation and a message explain rejected input or credentials. The initial screen also used a short entrance animation.
- **`lib/screens/auth/signup_screen.dart`:** I organized name, email, and password entry in one form. Validators run before calling the local sign-up method; duplicate email gets a message, while success opens the customer area. I dispose the controllers with the screen so they do not remain allocated.
- **Why I built them this way:** Keeping welcome, login, and sign-up separate gives each screen one clear job. I made the layout and visual decisions so the first step stays obvious and consistent with the bakery theme.

### AI-assisted Flutter/Dart code I understand best

- **Files:** `lib/screens/customer/ordering/payment_screen.dart`, `lib/screens/customer/ordering/confirmation_screen.dart`, `lib/providers/order_provider.dart`, `lib/services/payment_service.dart`.

- **My explanation:** The payment screen reads the cart or a reviewed order, validates the selected payment preference, checks daily batch capacity, and asks the customer to confirm the amount. I understand this because the steps keep the displayed confirmation and payment state aligned, while the local repository is a replaceable seam for a future real provider.
